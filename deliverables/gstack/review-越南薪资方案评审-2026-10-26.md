## 一、三个问题的直接回答

| 问题 | 回答 |
|---|---|
| **最严重的一条是什么** | **#1「适用范围声称覆盖计件员工，但全文只处理计时」**。这是唯一一条"方案边界错误"级别的问题：计件工资（单价 × 合格数量）与工时折算（时薪 × 折算工时）是两套并行的计薪通道，`salary_item.calc_mode` 里没有 `piece_rate`，`attendance_band_hour` 也没有产量维度。若越南厂真有人计件，一期上线的当天就会有一批人算不出工资；若没有，封面这句声明必须在发版前删掉，否则二期会被当成"欠交付"。**这条不是改代码能补的，是改范围。** |
| **有没有根本性错误** | **没有。** 三个核心判断我都复核过，站得住：①「Excel 是工时制、OA 是月薪制」这个根因判断正确（详见 §二.1，仅表述需收窄）；②10 段坍缩到 3 桶、6 段一致 4 段错、方向不一致的结论正确；③0–48h 轴 + 窗口交叠扣除的切片思路正确，且确实能根治 Excel 的 ⑧⑩ 漏扣。数据模型骨架（区间绑定 / 版本化时段集 / 分险种费率 / 批次快照）没有设计性错误，只有 #3、#7、#8 三处字段级缺口。 |
| **有没有必须补的章节** | **有两个半**。①**必须补**：`§5.6 漏打卡与多卡的归约规则`——现在 §5.1 假设"一行打卡 + 有进有出"，而工厂最常见的就是漏打卡、6 卡员工一天多行，这章不补一期写不出代码。②**必须补**：`§8 一期的验收例外条款`——现在"误差 <1 越盾"与 §9.3 的 `D-03` 直接打架。③**建议补**：`§12 计件工资的边界声明`——明确"本方案不覆盖计件，计件另立方案"，把封面的口子收掉。 |

## 二、评审意见清单

|---|---|---|---|---|
| **1** | **P0** | 封面「适用范围」（L9）＋全文 | 声明覆盖"计时/**计件**员工"，但 `salary_item.calc_mode` 只有 `fixed/base_ratio/ot_band/absent/late_early/perf_coef/perf_abs/manual`，**无计件单价模式**；`attendance_band_hour`/`attendance_month_stat` 无产量（合格数/报废数）维度；§5 五条链路全部以工时为唯一计薪驱动。计件工资无法用本方案表达 | 二选一：**(A)** 若厂内确有计件：新增 `salary_item.calc_mode='piece_rate'` + 产量来源表（对接现有 `ipqc`/报工数据），并在 §5 增加"链路六：产量 → 计件工资"，列为第二期。**(B)** 若全厂计时：把封面改为"全体**计时**员工"，并在正文加一句"计件工资不在本方案范围"。**建议先做 (B) 止血，再评估 (A)** |
| **2** | **P0** | §8 一期验收（L989）vs §9.3（L1073） | 一期验收写"OA 与 Excel 逐人比对 20 列，**误差 < 1 越盾**"，无例外。但 §9.3 的 `D-03` 明确承认"⑧⑩ 用餐漏扣是 Excel 的 bug，OA 修正后该列**必然**不等"。两条同时成立时，一期**永远无法通过验收**——这是验收标准的结构性矛盾，会导致一期无限延期或被迫"故意复刻 Excel 的 bug" | 验收改为**两层判定**：①**必须一致列**（C/E/F/G/H/K/L/M/N/O/P/Q/R + ①②③④⑤⑥⑦⑨ 工时）= 误差 < 1 越盾；②**豁免列**（⑧⑩ 工时及其派生的 D 列）= 由 HR 与财务**书面确认"以 OA 为准"**后豁免，同时在验收报告里附差异金额（每班 1.4~2.05 折算工时）。另建议把"逐越盾一致"改成"逐人一致 + 合计差额可解释"，更贴近实际验收场景 |
| **3** | **P0** | §4.9 `salary_record_line`（L637-656） | 缺"是否参与工资单合计"标志。`direction` 只有 `earning/deduction`，而公司社保（21.5%）按 §5.4 明确"不进 gross、不进 net"，写进本表后只能标 `deduction` → 前端/导出一旦按 `Σearning − Σdeduction = net` 对账，**每人都多出一笔 21.5% 的假扣款**。这是"表结构一旦上线就要数据迁移"的返工点 | 加两列：`affects_gross BOOLEAN`（进不进应发）、`affects_net BOOLEAN`（进不进实发），公司社保两列均为 `false`；或在 `direction` 里增加第三值 `info`（仅展示不计入）。同时把"`Σearning − Σdeduction = net`"写成表级约束/校验查询，防止后续再加项时重犯 |
| **4** | **P1** | §5.1 `sliceBands`（L775-781） | 每个时段在 0–48h 轴上"取与 `[in,out]` **交叠最大**的一个放置（k=0..2）"。正常场景（班次 ≤ 24h）等价于正确，但**班次跨度 > 24h 时同一时段会有两个放置都产生交叠，取 max 只计一份**。反例：05:00 上班、次日 09:00 下班（28h 连续值班/设备检修），⑥ 段（06:00-08:00）当日与次日各 2h，应得 4h，按 max 只算 2h → 少发 | 不用 max，改为**按日遍历累加**：`FOR dayOffset IN 0..1: 对该日 offsets 的每个 band 切片并累加`。这同时消解"② 晚间在 28h 班里出现两次"的问题，且不需要 k=2（当前 k 上界 2 与"48h 轴"的声明本身也不一致，可放到 64h）。改动很小，但要在 §5.1 明确写"轴上限 48h 与 k 上界必须一致，超出即 blocked" |
| **5** | **P1** | §5.1 `buildShiftInstance`（L711-740） | 伪代码假设"每人每天一行打卡、`check_in` 与 `check_out` 都存在"。真实数据里两个最常见的形态都没处理：**(a) `check_out IS NULL`**（忘打卡/卡机漏采）→ `outOff = minutes(null − base)` 直接 NaN，后续全部失真；**(b) 6 卡/4 卡员工一天多行**（`UNIQUE(user_id, work_date, check_in)` 允许一天 N 行）→ 取哪一行当 `actual_in/out` 没定义 | 补一节 **§5.6 归约规则**，明确三件事：①`actual_in = MIN(当日所有 check_in)`、`actual_out = MAX(当日所有 check_out)`；②**中间卡点（午出/午回）对时段计薪完全无用**——用餐扣除按固定钟点、不按实际离岗，所以 6 卡归位逻辑（现有 651 行 `computeRuleHours`）**不需要复刻进计薪链路**，只需服务迟到早退/缺卡判断。这条要显式写出来，否则开发会花 3~5 人日白做；③`actual_out IS NULL` 的三种处置：走 `miss_card` 补卡流程 / 按排班计划下班时刻兜底（标记 `estimated`）/ `blocked`。**默认建议兜底 + 标记**，否则漏卡的人当月无工资 |
| **6** | **P1** | §4.4（L358"区间重叠校验〔建议〕"） | 只靠 `UNIQUE(user_id, effective_from)` + 应用层校验。UNIQUE 只能防"同一天两条"，**防不住区间重叠**（2026-01-01~06-30 与 2026-03-01~12-31 并存 → 3 月起有两套架构，解析取哪条取决于查询写法，静默错）。文档把"触发器兜底"推到二期，**一期就会踩** | 一期就上 `EXCLUDE USING gist (user_id WITH =, daterange(effective_from, COALESCE(effective_to,'infinity'), '[]') WITH &&)`。**可行性必须写清两件事**：①需 `CREATE EXTENSION IF NOT EXISTS btree_gist`（`WITH =` 对 bigint 需要它），**该扩展通常需超级用户**，若生产库无权限则退化为 `BEFORE INSERT/UPDATE` 触发器（不推二期）；②`effective_to IS NULL` 必须用 `COALESCE(...,'infinity')` 包一层，否则 NULL 让 daterange 变无界、EXCLUDE 失效——这是最容易写错的一处 |

## 三、任务书点名五处的逐项判断

| 点名处 | 判断 | 说明 |
|---|---|---|
| **§1（实际 §2）「Excel 全工时折算 vs OA 月薪+加班附加」根因判断** | **站得住，但表述需收窄** | 核心判断正确：Excel `E = C × D` 已含加班倍率、**无独立加班科目**；OA `gross = base + ot_pay + allowances` 是月薪 + 附加。这是"数对不上"的真根因。唯一问题是把 Excel 整体称作"工时制"——G 列 5 项固定津贴是手填固定额（见 #10）。建议改为"**E 列工时制 + G 列固定额制的混合模型**" |
| **§3（实际 §4）DDL：字段是否够用 / 生成列 / exclusion 约束可行** | **骨架够用，三处缺口** | ①字段缺口：`salary_record_line` 缺"是否进合计"标志（#3，P0）；`attendance_month_stat` 唯一键与多版本冲突（#7）。②生成列 `adopted_rate` **可行**（PG≥12，需标注版本前置，见 #12）。③**exclusion 约束本方案没用，应该用**——`UNIQUE(user_id, effective_from)` 防不住区间重叠（#6）；`EXCLUDE USING gist` 可行但**必须 `btree_gist` 扩展 + 超级用户权限**，且 `effective_to IS NULL` 要 `COALESCE('infinity')`，两点都要写进文档，否则实施时会静默失效 |
| **§4（实际 §5.1）切片函数对「跨日 + 整班归属 + 4 段用餐」是否严密** | **用餐部分严密，跨日部分不严密** | ①**4 段用餐：严密且正确**——遍历全部窗口做 `MAX(0, MIN(三上界) − MAX(三下界))`，⑧⑩ 得 7.0h（而非 Excel 的 7.5h），确实根治了缺陷①；窗口用绝对钟点、与班次起止解耦，设计正确。②**整班归属起班日：方向对、缺约束**——依赖 `attendance_raw.work_date` 导入约定，库层无校验（§2.2 #12 已承认，但 §5.1 无对应拦截分支）。③**跨日：两处不严密**——(a)"取交叠最大放置"在 >24h 班次下少算（#4）；(b)`check_out IS NULL` 与一天多行完全未处理（#5，P1）。**结论：切片思路对，但 §5.1 只能算"主流程伪代码"，不能算"可实现的规格"**，必须补 §5.6 |
| **§7（实际 §8）分期是否合理 / 一期验收是否可操作** | **分期顺序正确，验收标准不可操作** | ①分期排序**正确**：一期"算得对不加界面"是对的（先证数学、再做人机），我认同这个取舍。②验收**不可操作**：与 §9.3 `D-03` 自相矛盾（#2，P0），必须改成两层判定 + 缺陷列书面豁免。③一期还差一条交付路径（数百人绑定无 CSV 通道，#9）。④工作量偏低（#14） |
