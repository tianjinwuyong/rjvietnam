# 现有流程改造成「电子流」方案对比与建议

**日期**：2026-10-21
**背景**：系统里已有 9 个审批入口分散在 6 个模块，各自实现状态机与权限判断；希望统一成电子流（在线审批、留痕、可配置）。

---

## 1. 现状盘点

| 模块 | 审批入口 | 现状 |
|---|---|---|
| 生产/领料 | 领料单审批（单张 + 批量） | 单级：生产主管 → approved |
| 生产/超领 | 超领单审批 | 单级 |
| 生产/补料 | 补料单审批 | 单级 |
| MRB | 预审（IQC 主管）→ 终审（质量经理） | 多级 + 会签评审员，逻辑最复杂 |
| 库存/盘点 | 盘点单审批 | 单级 |
| 库存/调拨 | 调拨单（部分有审批） | 单级/无 |
| IQC | 检验报告审批 | 单级 |
| 生产退料 | 退料 → IQC → 入库 | 串行多角色 |
| 工单 | 超耗（超补）审批 | 本次新增，单级 |

共性问题：

1. **审批逻辑写死在业务代码里**：加一个节点/换审批人 = 改代码 + 发版；
2. **状态机各自一套**：pending_approval / pending_review / pending_final… 名称不统一，跨模块做待办汇总困难；
3. **没有统一待办**：主管要逐个菜单找单子；
4. **留痕不完整**：谁批的、什么时候、意见是什么，部分模块只有最终结果；
5. **移动端弱**：PDA 只能处理部分流程。

---

## 2. 四个方案对比

### 方案 A｜轻量统一审批引擎（推荐）

自研一个「审批内核」，业务模块只负责「提交审批 / 接收审批结果」，节点和审批人配置化。

- 数据模型：`approval_flow_def`（流程定义）、`approval_node`（节点+条件）、`approval_instance`（单据实例）、`approval_task`（待办）、`approval_action_log`（留痕）；
- 节点类型：单人 / 角色 / 指定上级 / 会签（全通过）/ 或签（一人通过）/ 抄送；
- 条件路由：按数量、金额、工段、紧急度走不同分支（例如超耗 >3‰ 才进审批）；
- 动作：通过、驳回、撤回、转办、加签；
- 待办：统一「我的待办」页 + PDA 待办 + 站内消息（可选企微）；
- 与现有状态机关系：**业务表保留 status**，审批段交给引擎；引擎回调时业务更新自己的状态（如 picking: approved → issued）。

优点：改造面可控、配置化、可渐进迁移；缺点：要自研引擎与 UI（约 2~3 周）。

### 方案 B｜引入 BPMN 引擎（Flowable/Camunda + bpmn-js）

图形化编排、支持复杂网关、定时边界事件。

优点：功能最全、流程可视化；缺点：引入 Java 服务/额外部署、与现有 NestJS 技术栈割裂、学习与运维成本高。**除非流程会频繁大改，否则不划算。**

### 方案 C｜不引引擎，仅统一规范

每个模块加一张审批日志表，统一字段与接口风格。

优点：一周内可完成；缺点：节点配置仍需改代码，重复度高，长期维护差。适合「只想要留痕」的场景。

### 方案 D｜外挂企业微信/钉钉审批

业务提交后推送审批卡片到企微，审批结果回调写回。

优点：移动审批体验最好、无需自研审批 UI；缺点：依赖外部平台、权限映射复杂、内网/离线场景受限。适合作为**通知与移动审批的补充**，不建议作为唯一方案。

---

## 3. 推荐：A + D 组合

- 审批内核自研（A）；
- 通知/移动审批接企业微信（D，可选）；
- 分三期迁移，业务不中断。

### 3.1 目标架构

```
业务模块（领料/超领/MRB/盘点/退料…）
        │  submit(bizType, bizId, payload)
        ▼
   审批引擎（节点解析 / 条件路由 / 待办 / 留痕）
        │  onApproved / onRejected 回调
        ▼
业务状态机（approved / issued / received / closed …）
```

关键设计：

- **单据唯一键**：`(biz_type, biz_id)` 保证幂等，重复提交不产生多实例；
- **快照**：提交时把审批链快照到实例，后续改配置不影响在途单据；
- **权限**：节点解析优先级 指定人 > 角色 > 上级 > 兜底管理员；
- **并发**：审批动作走 CAS（`status='pending'` 才能更新），防重复点击；
- **超时**：节点支持 `timeout_hours`，超时提醒/自动升级（可配置）；
- **留痕**：每次动作写 action_log（人、时间、意见、附件）。

### 3.2 迁移顺序（按收益/风险排序）

| 期 | 范围 | 说明 |
|---|---|---|
| 一期 | 领料审批、超领、补料 | 单级、量大、改造简单，先跑通内核与待办 |
| 二期 | IQC 报告审批、盘点审批、调拨 | 单级但涉及多角色 |
| 三期 | MRB（预审/终审/评审员） | 多级会签，最复杂，最后迁 |
| 可选 | 生产退料、工单超耗 | 条件触发型审批，验证条件路由 |

### 3.3 双轨与回滚

- 用 feature flag `approval_engine_enabled` 按 bizType 灰度；
- 在途老单据仍走原逻辑，新单据走引擎；
- 引擎异常可一键回退旧路径，数据不迁移（只新增表）。

---

## 4. 需要业务先确认的 5 件事

1. 审批人怎么定：固定角色，还是按「工段/部门负责人」动态取？
2. 是否需要会签/或签？哪些流程需要？
3. 驳回后是退回发起人改，还是退到上一节点？
4. 是否需要代理/转办（请假场景）？
5. 移动端（PDA/企微）要覆盖哪些审批？

---

## 5. 工作量预估（方案 A）

| 项 | 预估 |
|---|---|
| 数据模型 + 引擎内核（节点解析/条件/回调/幂等） | 4~5 人日 |
| 流程配置界面（简单表单式，非图形化） | 3 人日 |
| 统一待办（PC + PDA） | 2 人日 |
| 接入领料/超领/补料 3 个流程 | 3 人日 |
| 二期、三期迁移 | 各 3~5 人日 |

---

> 结论：优先做 **方案 A（自研轻量审批内核）+ 分期迁移**，企微审批作为可选通知通道；不建议一上来上 BPMN。
