# MES → WMS 领料单接入 · 交付说明

**日期**：2026-10-31（首版），2026-10-31 晚修订：**改为只接领料单，不接工单**
**方向**：MES（192.168.6.27:8080）→ WMS（拉模式，WMS 定时调 MES）
**接口文档**：`docs/MES工单下发接口_对接文档_20261030.md`（v1.0，已归档进仓库）

---

## 〇之一、二次调整（2026-10-31 上午）

业务目标再往前提一步：**WMS 不要自己算单，要 MES 已经开好、已经审批的领料单原样搬过来。**

实测结论：MES 现有接口没有「领料单查询」，`/issue/list`、`/picking`、`/picking-orders` 全返回 404，
只有 `/mo`、`/mo/{no}`、`/mo/{no}/materials`、`/issue/pending` 四个可用。
`/issue/pending` 能拿到的仅限"还有缺口"的工单，且只有工单级字段 `issueNo`，没有单头人员、没有明细行。

因此分两步走：

| 步骤 | 内容 | 状态 |
|---|---|---|
| ① 过渡（已上线） | 仍用 `/issue/pending`，把**责任人**补齐 + 领料单列表显示 **MES 单号**，让仓库能对单、审计有名字 | ✅ 本次交付 |
| ② 正式（待 MES） | MES 开放 `GET /api/itf/wms/issue/list`（带单号/状态/下单人/批准人/明细），WMS 按 MES 单号一一落库 | ⏳ 需求已出 |

正式版接口需求见 **`docs/MES领料单查询接口需求-20261031.md`**（可直接转给 MES 维护人）。

### ① 过渡期改了什么

1. **对接操作人（新增配置）**
   MES 不返回下单人/批准人，台账上又不能空。在「MES 接入 → 接口配置 → 对接操作人」选一个 WMS 账号后：
   - 同步生成的领料单，`applicant_id` 和 `approver_id` 都写这个账号
   - `approval_remark` 写「MES 同步生成，由对接操作人代签生效」，审计能看清是代签、不是真人审批
   - 界面申请人/审批人列不再显示 `MES` 徽标，而是显示该账号姓名
   - 不选也能用，退回原来的"空审批人 + MES 徽标"
   - 选的时候必须选**有效账号**，选了不存在的 id 会被后端拒绝
2. **领料单列表新增「MES 单号」列**
   值来自工单上的 `mes_issue_no`（MES 侧已开的领料单号），手工单显示 `-`。
   仓库拿这一列跟 MES 台账对单，不用再靠工单号猜。
3. **单内备注带 MES 单号**
   有 `mes_issue_no` 时，领料单备注写成 `MES 工单 X / MES 领料单 Y 按用料自动生成（…）`。

### ② 正式版上线后怎么切

MES 接口一开，WMS 侧改动集中在 `mes-sync.service.ts`：新增 `syncIssues()`，按 `issueNo` 幂等 upsert，
状态直接映射、人员直接取 `createdBy/approvedBy`，**配了对接操作人时只在 MES 人员匹配不到 WMS 账号时才启用代签**。
过渡期生成的单（`PK` 开头）保留，不清理、不回改。

## 〇之二、发料结果回写 MES（2026-10-31 上午）

用户要求：**领料数据要回写 MES，用于工单结案**。方向从「MES → WMS」扩展到「WMS → MES」。

### 前提（必须让 MES 开接口）

MES 现有接口文档第七节写死：「这套接口是**只读**的：WMS 不能通过它改 MES 数据」。
所以回写不是配置一下就能通，**MES 必须新开一个写接口**，规格见
`docs/MES领料单查询接口需求-20261031.md` 第二节（`POST /api/itf/wms/issue/{issueNo}/issued`）。

WMS 侧已按「接口随时会开」把链路做完整了，接口一通、开关一开就能跑，不用改代码。

### 业务口径（用户确认）

| 项 | 口径 |
|---|---|
| 回写粒度 | **按 WMS 领料单逐单推**，发完一张推一张 |
| 结案触发 | **MES 自己按回写数据判断**，WMS 不额外发「可结案」信号 |
| 批次 | **要带**，取自发料时的库存出库流水 |

### WMS 侧实现

**1. 待回写队列 `mes_issue_writeback`**
- 为什么独立建表：一张单会有 issued / received / returned 多个事件，业务表加一列表达不了；
  重试次数、下次重试时间、最后错误属于投递状态，不该污染 `picking_order`
- 幂等键 `(picking_id, event_type)` 唯一；补料后再次发料会重置为 pending，用新快照重推

**2. 入队时机**
发料完成（`status` 变 `issued`）时**在发料事务内**插一条事件，与实发数量同提交——不会出现「料发了但事件没记」。
三个发料入口都覆盖：`pickMaterial`、`pickMaterialIncremental`、`pickWithSubstitution`。

**3. 推送**
- 独立定时器，每 60 秒扫一次 `pending AND next_retry_at <= now()`
- 只推 `source='mes'` 且拿得到 MES 单号的单；其余置 `skipped`，不报错
- 失败按 1 → 2 → 5 → 15 → 30 → 60 分钟退避，最多 8 次；超限置 `failed`，界面红色显示，可手动重推
- 开关 `mes.writeback_enabled` **默认关闭**，MES 接口没开时不会刷一堆 404

**4. 推送内容**
`issueNo` / `moNo` / `wmsPickingNo` / `workSection` / `issuedAt` / `issuedBy` / `idempotencyKey` /
`items[{materialCode, materialName, unit, actualQty, batchNo, reelNo}]`

- 数量取 `picking_order_item.actual_qty`（实发，不是申请量）
- 批次取 `inventory_transaction` 里 `tx_type='issue' AND reference_no=本单号` 的流水；同一物料跨批次时按各批出库量占比摊开，最后一行补差保证总和精确
- 无批次流水时批次留空、照推，不阻断（现场确实有不带批次的物料）
- 幂等键带版本：`wms:{pickingNo}:issued:v{单据更新时间毫秒}`，补发后再推不会被 MES 当重复吞掉

**5. 界面**
「MES 接入」新增「发料回写」页签：状态筛选、待推/已推/失败/无需回写计数、尝试次数、下次重试、最后错误、单条重推、「立即推送」。
顶部统计卡多两项：待回写 MES、回写失败（有失败时标红）。
「接口配置」多一个「发料结果回写 MES」开关。

**6. 接口**
`GET /api/mes-sync/writeback/list`、`POST /api/mes-sync/writeback/run`、`POST /api/mes-sync/writeback/:id/retry`

### 本期没做（要提前知道）

- **退料不回写**：`production_return` 只有工单号、没有领料单号，只能工单级回写，等 MES 明确结案口径再加。
  后果：MES 若按「发料量 = 消耗量」结案，有退料的工单会偏高
- **签收差异不回写**：签收短收的差额不推，避免重复累计；将来用 `eventType=received` 补
- **拆单对账口径要跟 MES 讲清楚**：一张 MES 领料单在 WMS 被拆成最多 3 张，MES 侧必须按
  `wmsPickingNo` 分片、同分片覆盖、结案时求和，**不能按收到请求次数累加**（已写进接口文档 2.4 节）

## 〇之三、职责边界：按「领料单来源」分治（2026-10-31 中午，含 12:40 修订）

用户最终口径：**「如果领料单是由 WMS 工单触发的，保留原有的 WMS 功能；如果领料单来源是 MES，
那么工单肯定也是 MES 下发的，最后结案也在 MES。」**

第一版按「工单来源」一刀切是错的——会误伤 WMS 自己开单的工单，也漏掉一个真实场景：
MES 工单号与手工工单撞车时（`upsertWorkOrder` 会跳过不覆盖），工单仍是 `manual`，
但 MES 领料单照样能挂上来。**所以判定必须看领料单来源，不能只看工单来源。**

### 判定规则（`resolveMesControl()`）

| # | 条件 | 结论 |
|---|---|---|
| 1 | 存在任意**未取消**、`source='mes'` 的领料单 | **MES 管控** → 拦截下发/撤回/结案/取消 |
| 2 | 有领料单，但都不是 MES 的 | **WMS 自管** → 原有功能全部保留 |
| 3 | 一张领料单都没有，且工单 `source='mes'` | **MES 管控** → 拦截（否则 WMS 抢先按 BOM 开单，与 MES 随后同步的领料单重复发料） |
| 4 | 一张领料单都没有，且工单 `manual` | **WMS 自管** → 照旧下发 |

> 已取消的 MES 领料单不参与判定：出现过「MES 单被取消后工单要重开」的情况，不能因为历史记录就锁死。

### 改了什么

| 位置 | 改动 | 效果 |
|---|---|---|
| `workorder.service.ts` 新增 `resolveMesControl()` | 按上表判定，返回 `{controlled, reason, mesIssueNos}` | 判定逻辑只有一处，列表和四个写入口共用同一口径 |
| 新增 `assertWorkOrderOperable()` | 命中管控即抛 400，提示带 MES 领料单号 / 工单号 | 现场能直接定位到 MES 的那张单 |
| `issueWorkOrder()`（下发） | 命中管控则拒绝 | 提示改为「领料单由 MES 下发，WMS 不再按 BOM 生成」 |
| `recallWorkOrder()`（撤回） | 命中管控则拒绝 | 撤回=取消待审批领料单+工单退回草稿，属于 MES 的排产动作 |
| `closeWorkOrder()`（结案） | 命中管控则拒绝 | **核心**：领料单来自 MES → 结案回 MES |
| `cancelWorkOrder()`（取消） | 命中管控则拒绝 | 同上，MES 侧取消后由同步映射成 `cancelled` |
| `getWorkOrderList()` / `getWorkOrderById()` | 返回 `source`/`mesMoNo`/`mesStatus`/**`mesControlled`** | `mesControlled` 用一条 SQL 复刻上面三条判定，前端不必自己算 |
| `WorkOrderList.tsx` | 仅当 `mesControlled` 时：工单号后加 `MES` 徽标、操作列显示「由 MES 管理」、不渲染按钮 | 其余工单按钮原样保留 |
| `shared/api.interface.ts` | `WorkOrder` 增 `source`/`mesMoNo`/`mesStatus`/`mesControlled` | 类型对齐 |

### 状态谁改

| 场景 | 工单状态谁改 | 说明 |
|---|---|---|
| 领料单来自 MES | **MES** | `mapStatus()` 映射，已关闭 → `closed`、已取消 → `cancelled` |
| 领料单由 WMS 工单自己开 | **WMS**（下发/撤回/结案/取消，功能不变） | 与接入 MES 前完全一致 |

`mapStatus()` 原有防回退逻辑保留：`closed`/`cancelled` 不会被 MES 的旧状态拉回，
`released` 不会因为 MES 仍显示「已排产」而退回 `created`。
即「WMS 已结案的手工单」不会因为 MES 也在同步同号工单而被重置。

## 〇、定位（这一版最重要的一句话）

WMS 这边**只要领料单**：MES 把"哪张单、哪个工段、要发多少料"给过来，WMS 生成领料单，仓库照着发。

所以数据入口**只有一个**——`GET /api/itf/wms/issue/pending`（文档 3.5，原文写的就是"仓库轮询首选"）。
不再拉 `/mo` 全量工单清单，也不做全量工单同步：

- 没缺口的工单既不开单、也没人看，拉进来只是往库里灌数据
- 工单状态变化（已排产→生产中→完工）对"发料"这件事没有影响
- 少一个同步任务，就少一处会出错的地方

## 一、为什么选「拉」不选「推」

| 通道 | 谁主动 | 是否需要 MES 改代码 | 本方案 |
|---|---|---|---|
| 拉 | WMS 定时调 `/issue/pending` | 不用 | ✅ 采用 |
| 推 | MES POST 到 WMS | 要 MES 新增接收接口 | 暂不做 |

联调只需要在 WMS 填一个地址 + 密钥；MES 那边零改动；出问题只影响 WMS 的同步任务，不会因为推送把 WMS 打挂。

## 二、数据怎么落

### 1. 工单：只做「抬头」，不做业务

**这一条要特别说明**：`picking_order.work_order_id` 是 `NOT NULL` 且有外键指向 `work_order`，WMS 里领料单、发料、退料、超耗、追溯共 12 处查询都 `innerJoin(work_order)`。
把这一列改成可空，等于把整套发料流程都改成"可能没有工单"，风险和收益不成比例。

所以处理方式是：**同步到待领料工单时，顺手补一行最小工单**，只填领料单必须的字段（工单号 = MES 的 `moNo`、产品编码/名称、计划数量、日期、`source='mes'`）。

- 不做 BOM 展开、不生成物料需求单、不需要任何人维护
- 工单号直接沿用 MES 的 `moNo`，两套系统对账用同一个键
- 若 MES 侧只回了工单号（没带产品/数量），会**单张补一次** `/mo/{moNo}` 详情，不触发全量拉取
- 同工单号若已是 WMS 手工建的工单，只记"跳过"，绝不覆盖

### 2. 用料明细：`mes_work_order_material` 快照表

MES 的接口只给当前值、没有历史；WMS 算缺口、事后追溯都要"那一刻的需求"。按 `(mo_no, 物料, 位号)` 落一份快照，每轮**先删后插**（MES 删行时 WMS 不会残留）。

### 3. 领料单：按工段生成，`picking_order.source='mes'`

- 一个工段一张单（SMT / DIP / 组装 / 包装），数量取「建议发料量 `suggestIssueQty`（已按 MPQ 取整）」或「缺口 `openQty`」，界面可切换
- **幂等**：重复同步不会重复开单，只刷新**未发料**的数量；已发料的一律不动
- 表头沿用 WMS 现有单号规则 `PK+日期+流水`
- 生成的单 **默认直接 `approved`（已生效）**，立即可在「领料单」发料列表里发料，不再需要生产主管审批；`approval_time` 写入生成时刻、`approval_remark` 写「MES 自动生效（免审批）」，追溯链不断
- 想保留审批环节：在「MES 接入 → 接口配置」关掉「领料单自动生效（免审批）」，之后新单回到 `pending_approval`；重新打开后，下一轮同步会把还压着的历史待审批 MES 单一并补生效
- 申请人列为空，界面显示 `MES` 徽标标明来源（审批人列为空是正常的，因为本来就没走人工审批）

## 三、完整链路（已实测跑通）

```
WMS 定时（默认 5 分钟）
  └─ GET /issue/pending           拿到「有缺口的工单 + 该单各工段用料」
      ├─ 补/更新抬头工单           work_order.source='mes'
      ├─ 落用料快照               mes_work_order_material
      └─ 按工段开单（可选自动）    picking_order.source='mes'，status='approved'（默认生效）
                                    ↓
             仓库「工单管理 → 领料单」直接发料（默认只看已生效）
             ※ 关掉「领料单自动生效」时，中间会多一步：
               生产主管「生产管理 → 领料审批」批量通过
```

## 四、状态与工段映射（易错点，改动请从这里改）

工单状态映射仍保留（抬头工单上会显示 MES 状态）：

| MES 工单状态 | WMS 工单状态 |
|---|---|
| 已排产 / 待排产 / 待生产 | `created` |
| 生产中 / 在制 / 已开工 | `in_production` |
| 已完工 / 完工 | `completed` |
| 已关闭 | `closed` |
| 已取消 | `cancelled` |

保护规则：已 `closed`/`cancelled` 的不会被 MES 拉回；已 `released`（开过领料单）的不会因 MES 显示"已排产"而退回 `created`，否则每轮同步状态来回翻转。

| MES 用料段 `segment` | WMS 工段 `work_section` |
|---|---|
| SMT | `smt` |
| 插件 / 后焊 | `dip` |
| 组装 / 装配 / 测试 | `assembly` |
| 包装 / 包材 | `packing` |
| **辅料** | `packing`（WMS 只有四个工段；现场口径不同就改 `SEGMENT_MAP` 一处） |

## 六、上线操作（现场两步）

1. 「工单管理 → MES 领料接入 → 接口配置」：地址默认已是 `http://192.168.6.27:8080`（不带 `/api/itf/wms`），把**密钥**粘进去（MES「订单管理 → 工单下发 WMS」右上角复制），点「测试连接」，看到 `连接成功：ruijing-mes，xx ms，MES 时间 …` 即通

只想先看一眼不自动跑：填完密钥点一次「同步领料需求」，到「待开单」页签核对缺口、未匹配物料，确认无误再开开关。

## 八、已知边界（要提前知道）

1. **MES 有、WMS 没建档的物料**：照样进领料单（保证与 MES 需求一致），但 `material_id` 为空，**发料时会卡住**。开单结果里会提示"有 N 条物料未建档，请先在物料主数据补建"，待开单表也有「未匹配物料」红标。
2. **领料单默认免审批**：MES 单生成即生效（`approved`），直接进仓库发料列表，不再经过「领料审批」。这是本轮的明确要求；如需恢复审批内控，关掉配置页的「领料单自动生效（免审批）」即可，不用改代码。
3. **申请人显示为 `MES` 徽标**：自动单没有人工申请人，列表与审批页按 `source='mes'` 标出来源。
4. **辅料**归到包装工段。
5. ~~单向下行：WMS 不回写发料结果给 MES~~ → 已在「〇之二」补上回写队列，开关 `mes.writeback_enabled` 控制，MES 接口开通后启用。
6. **按领料单来源分治**（见「〇之三」）：领料单来自 MES 的工单，WMS 不提供下发/撤回/结案/取消（操作列显示「由 MES 管理」）；领料单由 WMS 工单自己开的，功能与接入 MES 前完全一致。现场问"结案按钮去哪了"，先看这张单的领料单是不是 MES 来的。
