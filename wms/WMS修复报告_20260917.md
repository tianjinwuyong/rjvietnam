## 二、致命BUG修复（4个）

### BUG-005：扫码收货重码竞态（并发重复入账）

- **根因**：verifyQr检查与insert之间存在时间窗口，并发时多个请求同时通过检查
- **修复方式**：
  1. **数据库层**：清理receipt_order表中3条重复数据，新增唯一索引 `idx_receipt_qr_content_unique ON receipt_order(qr_content)`
  2. **代码层**：scanReceipt和batchReceipt的insert放入事务内，事务内先 `SELECT ... FOR UPDATE` 预检，insert用try/catch捕获Postgres唯一约束冲突（错误码23505，兼容Drizzle包装的err.cause.code），冲突时抛ConflictException("该标签已被扫码收货，请勿重复扫描")
- **修改文件**：`server/modules/receipt/receipt.service.ts`
- **验证结果**：5并发扫同一标签 → 1个成功(201) + 4个409重码拒绝 + 0个500 ✅

### BUG-008：BOM工段中文/大写时工单下发0领料单

- **根因**：BOM中work_section存'SMT'/'组装'/'包装'，代码常量WORK_SECTIONS仅认小写英文'smt'/'dip'/'assembly'/'packing'，键名不匹配
- **修复方式**：
  1. 新增 `normalizeWorkSection()` 工具函数：trim → 中文映射（组装/装配→assembly, 包装→packing, 测试→testing）→ 英文toLowerCase → 未知值默认'smt'
  2. 在4处按工段分组的位置统一调用：previewMaterialRequirement、generateMaterialRequirement、issueWorkOrder、createSupplement
- **修改文件**：`server/modules/workorder/workorder.service.ts`
- **验证结果**：工段映射函数已应用到所有4处，编译通过 ✅

### BUG-009：并发下发同一工单无保护（重复生成领料单）

- **根因**：issueWorkOrder先查existingPicking再insert，无行锁或唯一约束保护
- **修复方式**：
  1. **数据库层**：work_order表新增 `version` 字段（integer，默认0）用于乐观锁
  2. **代码层**：issueWorkOrder全部逻辑移入事务，事务内先 `SELECT ... FOR UPDATE` 锁工单行，锁后校验status（非created/pending则抛ConflictException），再查picking_order是否已存在（有则抛ConflictException("该工单已生成领料单，请勿重复下发")），最后生成领料单+更新status='released'+version+1
  3. 同样的并发保护加到approveRequirement和batchApprovePickingOrders
- **修改文件**：`server/modules/workorder/workorder.service.ts`、`server/database/schema.ts`
- **验证结果**：新建工单后5并发下发 → 1个成功(201，生成领料单) + 4个409冲突拒绝 + 0个500 ✅

### BUG-013：库存调整允许负数量

- **根因**：adjustInventory无数量校验，发料/调拨扣减无防负库存保护
- **修复方式**：
  1. adjustInventory入口校验 actualQty >= 0（负数抛BadRequestException("调整数量不能为负数")）
  2. doMoveSingle和doTransfer的源库存扣减改为条件UPDATE：`WHERE id=? AND quantity>=?` + returning()检查affectedRows，为0抛ConflictException("库存不足，扣减后将为负")
  3. workorder.service.ts中3处领料扣减（pickMaterial、pickMaterialIncremental、pickWithSubstitution）同样加条件UPDATE防负库存
- **修改文件**：`server/modules/inventory/inventory.service.ts`、`server/modules/workorder/workorder.service.ts`
- **验证结果**：actualQty=-5 → HTTP 400 "调整数量不能为负数" ✅

## 三、严重BUG修复（8个）

### BUG-001/007：IQC审批无角色校验（检验员可自批）

- **修复方式**：iqc.controller.ts中report/:id/review、report/:id/reject、report/batch-approve三个接口加 `@NeedRoles('iqc_manager', 'admin', 'quality_manager')`，检验员调用返回403
- **修改文件**：`server/modules/iqc/iqc.controller.ts`

### BUG-002/003/006：系统管理接口无角色守卫

- **修复方式**：system.controller.ts中除login（公开）和logout（需登录）外，20个系统管理接口（参数/角色/账号/操作日志/批量库位生成）全部加 `@NeedRoles('admin')`
- **修改文件**：`server/modules/system/system.controller.ts`
- **验证结果**：iqc_inspector token访问 /api/system/account/list → HTTP 403 ✅；admin访问 → HTTP 200 ✅

### BUG-004：IQC主管可创建收货单（跨角色越权）

- **修复方式**：receipt.controller.ts中scan和batch-receipt接口加 `@NeedRoles('wh_keeper', 'wh_manager', 'admin')`
- **修改文件**：`server/modules/receipt/receipt.controller.ts`
- **验证结果**：iqc_inspector调用 /api/receipt/scan → HTTP 403 ✅

### BUG-010：超期物料发料提示不友好

- **修复方式**：workorder.service.ts新增 `buildExpiredStockMessage()` 私有方法，查询超期批次详情（批次号、超期天数、所在库位），拼装详细提示信息，3处发料超期校验（pickMaterial、pickMaterialIncremental、pickWithSubstitution）统一调用
- **提示示例**：`物料TEST-EL-020（批次B20260901已超期15天（库位A-01-02））禁止发料。请先将该批次库存移至复检库位并提交超期复检申请。`
- **修改文件**：`server/modules/workorder/workorder.service.ts`

### BUG-014：并发库内调拨65%返回500

- **根因**：目标库位检查+INSERT非原子，并发时都查不到目标库存都INSERT，命中唯一约束冲突→500
- **修复方式**：
  1. doMoveSingle和doTransfer中目标库存创建/更新改为 `INSERT ... onConflictDoUpdate({target:[materialId,locationId,batchNo,stockStatus], set:{quantity: sql\`inventory.quantity + excluded.quantity\`}})\` 原子upsert
  2. 整个调拨流程在事务内：源库存行FOR UPDATE锁 → 检查数量 → 条件扣减 → upsert目标库存 → 写调拨记录 → COMMIT
- **修改文件**：`server/modules/inventory/inventory.service.ts`
- **验证结果**：10并发调拨 → 0个500错误（原65%返回500）✅

### BUG-015：编辑库位接口返回500

- **根因**：warehouse.service.ts中updateLocation的patch映射漏了description字段，前端传{description}时patch为空对象，Drizzle生成无效SQL
- **修复方式**：patch增加description映射；增加空patch保护（Object.keys(patch).length===0抛400）；getLocationById补选description；WarehouseLocation接口增加description字段
- **修改文件**：`server/modules/warehouse/warehouse.service.ts`、`shared/api.interface.ts`

### BUG-017：仓管员越权操作返回500而非403

- **修复方式**：warehouse.controller.ts中仓库/库位的增删改6个接口加 `@NeedRoles('wh_manager', 'admin')`，越权抛ForbiddenException（GlobalExceptionFilter正确处理为HTTP 403）
- **修改文件**：`server/modules/warehouse/warehouse.controller.ts`
- **验证结果**：wh_keeper调用 POST /api/warehouse → HTTP 403 ✅

## 四、一般BUG修复（7个）

### BUG-011：补料单创建时workSection大小写不一致

### BUG-012：替代料按物料查询接口返回字段名不一致

- **修改文件**：`server/modules/inventory/inventory.service.ts`

### BUG-018：调拨存在TOCTOU竞态条件（超卖风险）

- **修复方式**：doMoveSingle和doTransfer中源库存查询加 `.for('update')` 行锁，锁后复查数量再扣减（与BUG-013的条件UPDATE互补：行锁防竞态，条件UPDATE防负库存）
- **修改文件**：`server/modules/inventory/inventory.service.ts`

### BUG-019：高并发查询响应时间劣化

- **修复方式**：inventory表新增3个复合索引：
  - `idx_inventory_location_status(location_id, stock_status)`

## 七、基础设施新增

### 新建文件（3个）

| 文件                                      | 作用                                                                           |
| --------------------------------------- | ---------------------------------------------------------------------------- |
| `server/common/auth/roles.decorator.ts` | 定义ROLES_KEY与@Roles(...roles)元数据装饰器                                           |
| `server/common/auth/roles.guard.ts`     | RolesGuard：从request.userContext.roleCode取角色，不在允许列表抛ForbiddenException        |
| `server/common/auth/auth.decorator.ts`  | 组合装饰器@NeedRoles(...roles)，单次UseGuards(JwtAuthGuard, RolesGuard)确保先JWT解析再角色校验 |

**关键设计**：使用单次UseGuards(JwtAuthGuard, RolesGuard)而非三层装饰器堆叠，避免NestJS守卫执行顺序导致RolesGuard先于JwtAuthGuard运行（会误判所有用户为403）。
